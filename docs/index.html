Willkommen bei ShopCore

Du kommst zu einem fiktiven Unternehmen, das Produkte online verkauft. Das Unternehmen hat ein kleines Python-Backend. Das Team möchte Änderungen besser absichern, bevor neue Funktionen die Kundschaft erreichen.

Die Geschichte des Unternehmens
ShopCore wächst. Entwicklerinnen und Entwickler können die Anwendung starten und einige Beispiele manuell ausprobieren. Es gibt jedoch keine zuverlässige Möglichkeit zu prüfen, ob das bisherige Verhalten nach einer Änderung noch funktioniert. Ein Fehler bei der Warenkorbsumme oder der Bestandsprüfung könnte dazu führen, dass jemand falsch belastet oder eine nicht erfüllbare Bestellung angenommen wird.

Deine Rolle

Du entwickelst im ShopCore-Team. Deine Aufgabe ist nicht nur, eine angeforderte Funktion einmal zum Laufen zu bringen. Du machst das erwartete Verhalten verständlich und prüfst es automatisiert, damit das Team die Software weiterhin mit Vertrauen ändern kann.

Danach kannst du …

  • Erklären, warum automatisierte Tests nützlich sind.
  • pytest-Tests schreiben und ausführen.
  • Normale, grenzwertige und ungültige Fälle auswählen.
  • Prüfen, ob der Code erwartete Ausnahmen auslöst.
  • Datenstrukturen refaktorieren und dabei das Verhalten erhalten.
  • Parametrisierung und Fixtures sinnvoll einsetzen.
  • Regressionstests und einen einfachen CI-Ablauf erklären.

So arbeitest du

  • Führe ein eigenes Repository und committe regelmäßig deinen Fortschritt.
  • Arbeite allein oder bilde ein Zweierteam zum Besprechen und Überprüfen.
  • Übersetze Anforderungen vor dem Programmieren in Beispiele.
  • Lies bei einem fehlgeschlagenen Test zuerst die Fehlermeldung, bevor du den Code änderst.
  • Vergleicht in gemeinsamen Diskussionen eure Entscheidungen, nicht nur eure Antworten.

Das Tempo ist bewusst flexibel. Jedes Kapitel ist eine Lerneinheit, kein Wettrennen. Schließe den Kontrollpunkt ab, bevor du weitermachst.

Ausgangscode

# shopcore/pricing.py

def calculate_total(items: list) -> float:
    total = 0

    for item in items:
        total += item.get("price") * item.get("quantity")

Füge folgenden Code in die Datei src/shopcore/main.py ein:

Wir haben jedoch noch nicht geprüft, ob die Funktion auch für andere Eingaben korrekt arbeitet. Wir müssen das Verhalten der Funktion genauer untersuchen.

Dein erster automatisierter Test

Ziel: Verstehe den Aufbau eines Tests und führe ihn mit pytest aus.

Was ist ein automatisierter Test?

Ein automatisierter Test führt Code mit einer bekannten Eingabe aus und prüft, ob das beobachtete Ergebnis dem erwarteten entspricht. Er lässt sich wiederholt, schnell und zuverlässig ausführen. Ein Test ist ausführbare Dokumentation eines Verhaltens, das dem Team wichtig ist.

Es gibt verschiedene Frameworks zum Testen, z.B. pytest, unittest und nose. Alle haben ihre Vor- und Nachteile. Wir werden pytest verwenden. Pytest ist ein weit verbreitetes und beliebtes Framework, ist einfach zu bedienen und bietet trotzdem viele Features zum Testen von Python-Code.

Pytest hinzufügen

Füge pytest als Entwicklungsabhängigkeit hinzu:

uv add --dev pytest

Führe pytest aus, um zu prüfen, ob es korrekt installiert ist:

uv run pytest --version

Du solltest eine Ausgabe ähnlich wie diese sehen: pytest 7.4.0 Die Versionsnummer kann abweichen.

Um pytest auszuführen, verwende den Befehl: 
uv run pytest
Pytest sucht automatisch nach Testdateien und Testfunktionen. Standardmäßig heißen Testdateien test_*.py oder *_test.py. Testfunktionen müssen mit test_ beginnen. Da wir noch keine Testdateien haben, wird pytest keine Tests finden. Du solltest eine Ausgabe ähnlich wie diese sehen: 
============================= test session starts ==============================
...
collected 0 items
============================== no tests ran in 0.00s ==============================

Wenn keine Tests gefunden werden, beendet sich pytest mit Exit-Code 5. Das ist hier zu erwarten.

Ordner für Tests anlegen

Erstelle einen neuen Ordner tests im Projektstammverzeichnis. Darin werden wir unsere Tests ablegen.

Hinweis: Lege Testdateien beispielsweise als test_pricing.py an.

Aufgabe 2A · Schreibe einen Test

Lege tests/test_pricing.py mit folgendem Inhalt an: 
from shopcore.pricing import calculate_total


def test_calculate_total():
    items = [
        {"price": 10, "quantity": 2},
        {"price": 5, "quantity": 3},
    ]

    result = calculate_total(items)

    assert result == 35

Hinweis: Entferne aus main.py sowohl die manuelle Funktion test_calculate_total als auch ihren Aufruf in run().

Um den Test auszuführen, verwende den Befehl: 
uv run pytest

Die Ausgabe sollte zeigen, dass der Test erfolgreich ist.

================================================================ test session starts ================================================================
...
collected 1 item                                                                                                                                    

tests/test_pricing.py .                                                                                                                       [100%]

================================================================= 1 passed in 0.02s =================================================================
👍 Super
Du hast deinen ersten Test mit pytest geschrieben und erfolgreich ausgeführt.

Aber lass uns nochmal anschauen was wir gerade gemacht haben. Wir haben die Eingabedaten vorbereitet, die Funktion aufgerufen und das Ergebnis überprüft. Das ist das Arrange-Act-Assert-Muster, das wir in den nächsten Kapiteln noch öfter verwenden werden.

Verstehe Arrange · Act · Assert

Vorbereiten (Arrange)

Bereite die Eingabedaten vor. Hier ist die Liste der Warenkorbartikel die Testvorbereitung.

Ausführen (Act)

Rufe die zu testende Funktion auf: calculate_total(items).

Prüfen (Assert)

Prüfe das Ergebnis: assert result == 35.

Beobachten

pytest meldet mit hilfreichem Kontext, ob die Prüfung bestanden wurde oder fehlgeschlagen ist.

Aufgabe 2B · Bringe den Test absichtlich zum Fehlschlagen

Ändere den erwarteten Wert vorübergehend in 34. Führe pytest aus und lies die Fehlermeldung. Setze den Wert anschließend wieder auf 35.
  • Was hat dir pytest mitgeteilt?
  • Warum ist das hilfreicher als eine print-Anweisung?
  • Warum ist ein fehlgeschlagener Test nicht zwangsläufig ein fehlerhafter Test?
Kontrollpunkt 2
  • Du hast einen Test geschrieben, der die Funktion calculate_total prüft.
  • Du kannst das Arrange–Act–Assert-Muster erklären und eine einfache pytest-Fehlermeldung lesen.
Impuls für die gemeinsame Diskussion

Besprecht den Unterschied zwischen „das Programm hat etwas Plausibles ausgegeben“ und „das Programm hat eine Erwartung geprüft“. Führt den Gedanken ein, dass ein Test nur für das Verhalten bestehen kann, das er tatsächlich prüft.

Grenzfälle und einen Fehler finden

Ziel: Erweitere Tests über den Erfolgsfall hinaus.
Präzisierung durch die Produktverantwortung
„Ein leerer Warenkorb hat die Summe 0. Ein Warenkorbartikel mit negativem Preis oder negativer Menge ist ungültig. Ungültige Artikel sollen abgewiesen werden, statt eine unsinnige Summe zu berechnen.“

Ideen zum Testen

Eine nützliche Testsuite umfasst verschiedene Eingabekategorien. Ein „Grenzfall“ liegt nahe an einem Grenzwert oder beschreibt eine ungewöhnliche, aber relevante Situation – nicht einfach einen extremen Zufallswert.

  • Erfolgsfall: gewöhnliche, gültige Daten.
  • Grenzfall: leerer Warenkorb, Menge 0.
  • Ungültige Eingabe: negativer Preis oder negative Menge.
  • Mehrere Artikel: sicherstellen, dass alle Zwischensummen berücksichtigt werden.

Aufgabe 3A · Ergänze Tests für das vereinbarte Verhalten

Ergänze einen Test für den leeren Warenkorb: 
def test_empty_cart():
    assert calculate_total([]) == 0
Plane außerdem Tests für negative Preise und negative Mengen. Notiere zunächst, welches Verhalten du erwartest. Im nächsten Kapitel schreiben wir die Tests für die Zurückweisung.

Aufgabe 3B · Finde den Fehler

Führe die aktuelle Funktion mit dieser Eingabe aus: 
[{"price": 10, "quantity": -2}]
Sie liefert -20. Laut Produktverantwortung müssen ungültige Daten zurückgewiesen werden. Die Implementierung erfüllt die präzisierte Anforderung also nicht.
  • Beschreibe den Fehler in einem Satz.
  • Welche Testeingabe macht ihn sichtbar?
  • Würdest du die Anforderung oder den Code ändern? Warum?
Kontrollpunkt 3
Dein kurzer Testplan umfasst normale, leere, grenzwertige und ungültige Eingaben. Du kannst erklären, gegen welche Anforderung der aktuelle Code verstößt.
Impuls für die gemeinsame Diskussion

Vergleicht eure Testideen zu zweit. Welche Fälle unterscheiden sich wirklich? Was ist redundant? Welche erwarteten Ergebnisse ergeben sich aus der Geschäftsanforderung und welche beruhen auf persönlichen Annahmen?

Fehler und Ausnahmen testen

Ziel: Prüfe, ob ungültige Vorgänge wie vorgesehen abgewiesen werden.

Konzept: Fehler können erwartetes Verhalten sein

Bei ungültigen Eingaben kann eine Funktion eine Ausnahme auslösen, statt eine Zahl zurückzugeben. Pythons ValueError signalisiert passend, dass ein Wert ungeeignet ist. Ein Test sollte prüfen, ob die Ausnahme wie erwartet auftritt.

Aufgabe 4A · Teste die Ausnahme

Ergänze diesen Test für eine negative Menge: 
import pytest


def test_negative_quantity_is_rejected():
    items = [{"price": 10, "quantity": -2}]

    with pytest.raises(ValueError):
        calculate_total(items)
Ergänze einen ähnlichen Test für einen negativen Preis. Führe pytest aus. Die neuen Tests sollten fehlschlagen, bis die Implementierung diese Werte zurückweist.

Aufgabe 4B · Setze die Anforderung um

Ändere calculate_total() so, dass bei einem negativen Preis oder einer negativen Menge ValueError ausgelöst wird. Das Verhalten für einen leeren Warenkorb bleibt erhalten.
Entscheidung zum Entwurf: Laut Kursanforderung sind negative Werte ungültig. Ob fehlende Schlüssel, Zeichenketten, boolesche Werte oder andere Typen behandelt werden müssen, ist noch nicht festgelegt. Erfinde nicht stillschweigend ein umfassendes Validierungsframework. Halte offene Fragen fest.

Nachdenken und besprechen

  • Warum ist pytest.raises() besser, als im Test jede beliebige Ausnahme abzufangen?
  • Was wäre, wenn die Funktion statt ValueError ein TypeError auslöste?
  • Sollte ein Test die Ausnahmemeldung prüfen? Wann wäre die Meldung Teil des Vertrags?
Kontrollpunkt 4
Alle Tests bestehen. Ungültige negative Werte lösen ValueError aus, und ein leerer Warenkorb ergibt 0.

Wandle Dictionaries in eine Dataclass um

Ziel: Ändere die interne Darstellung, ohne das Geschäftsverhalten zu verändern.
Refactoring-Auftrag #12 · Warenkorbartikel explizit darstellen

Der Preiscode hängt derzeit von Dictionary-Schlüsseln ab. Ein eigener Typ kann die erwartete Struktur der Warenkorbartikel deutlicher machen.

Wir möchten einen klaren Python-Typ, der einen Warenkorbartikel darstellt. Stelle auf eine Dataclass um, ohne das Verhalten der Preisberechnung zu ändern.

Konzept: Refactoring

Beim Refactoring wird die interne Struktur des Codes geändert, ohne sein von außen beobachtbares Verhalten zu verändern. Tests liefern Hinweise darauf, dass das Verhalten gleich bleibt. Wenn sich die Darstellung der Eingaben ändert, muss möglicherweise die Testvorbereitung angepasst werden; die fachlichen Erwartungen sollten stabil bleiben.

Aufgabe 5A · Erstelle die Dataclass

Erstelle src/shopcore/models.py: 
from dataclasses import dataclass


@dataclass
class CartItem:
    price: float
    quantity: int

Die Typannotationen dokumentieren die erwarteten Typen, validieren sie aber nicht automatisch zur Laufzeit. Die bereits vereinbarte Prüfung negativer Werte bleibt weiterhin notwendig.

Aufgabe 5B · Refaktoriere die Tests

Ändere die Testdaten von Dictionaries items = [{"price": 10, "quantity": -2}] zu der neuen Dataclass-Instanz items = [CartItem(price=10, quantity=-2)]. Behalte die erwarteten Summen und Ausnahmen bei.

Aufgabe 5C · Refaktoriere die Funktion

Ändere calculate_total(), sodass die Funktion statt Dictionary-Schlüsseln die Attribute der Dataclass ausliest. Verbessere die Typannotation zu list[CartItem] um Sie klarer zu machen.

Aufgabe 5D · Tests erneut ausführen

Führe die Tests erneut aus, um sicherzustellen, dass alles wie erwartet funktioniert.

Gemeinsame Überprüfung

  • Welche Zeilen im Anwendungscode haben sich geändert?
  • Welche Zeilen in den Tests haben sich geändert?
  • Welche Prüfungen sind gleich geblieben?
  • Wie machen die Dataclass-Attribute die Datenstruktur verständlicher?
  • Hat das Refactoring versehentlich ein Verhalten geändert?
Kontrollpunkt 5
Die Testsuite besteht nach dem Refactoring. Du kannst erklären, warum sich die Testvorbereitung geändert hat, die Verhaltenserwartungen aber nicht.
gemeinsame Diskussion

Macht den Unterschied deutlich: Tests müssen nach einem strukturellen Refactoring nicht textlich identisch bleiben. Sie sollten weiterhin dasselbe öffentliche Verhalten prüfen. Vermeidet Tests, die von irrelevanten Implementierungsdetails abhängen.

Ähnliche Tests parametrisieren

Ziel: Prüfe verschiedene Beispiele, ohne denselben Testkörper zu wiederholen.

Konzept: Parametrisierung

Wenn dieselbe Regel für mehrere Eingaben gelten soll, kann pytest eine Testfunktion mit verschiedenen Parametersätzen ausführen. So bleibt die Absicht des Tests sichtbar und Wiederholungen werden reduziert.

Aufgabe 6A · Prüfe Artikelsummen mit mehreren Beispielen

Beginne mit einem parametrisierten Test. Dieses Beispiel prüft die ShopCore-Funktion mit verschiedenen Artikeln. 
import pytest
      from shopcore.models import CartItem
      from shopcore.pricing import calculate_total


@pytest.mark.parametrize(
    "price, quantity, expected",
    [
        (10, 2, 20),
        (5, 3, 15),
        (0, 10, 0),
        (2.5, 4, 10),
    ],
)
def test_item_subtotal(price, quantity, expected):
  assert calculate_total([CartItem(price=price, quantity=quantity)]) == expected

Wie viele Testfälle führt pytest für diese eine Testfunktion aus?

Aufgabe 6B · Parametrisiere das Warenkorbverhalten

Erstelle einen parametrisierten Test test_valid_carts für mehrere gültige Warenkörbe und die erwarteten Summen. Verwende die nach dem Refactoring eingeführten Dataclass-Instanzen. Halte Tests für ungültige Eingaben lesbar; parametrisiere sie nur, wenn ihre Struktur tatsächlich gleich ist.

Rückblick

  • Welche Wiederholungen hat die Parametrisierung beseitigt?
  • Wann würden einzelne Testfunktionen die Absicht klarer vermitteln?
  • Wie kennzeichnet pytest die einzelnen Parameterfälle in der Ausgabe?
Kontrollpunkt 6
Du kannst mit @pytest.mark.parametrize mehrere Beispiele testen und dabei die erwarteten Werte explizit angeben.

Funktionswunsch: Rabattcodes

Ziel: Wende den Testablauf auf eine neue Funktion an.
Issue #43: Feature Request

Aktionsrabatt

„Kundinnen und Kunden können den Code SAVE10 eingeben und erhalten 10 % Rabatt auf ihren Warenkorb. Bei Codes wird nicht zwischen Groß- und Kleinschreibung unterschieden. Unbekannte Codes ändern die Summe nicht.“

Akzeptanzkriterien / Geschäftsregeln

  • SAVE10 verringert die Summe um 10 %.
  • save10 und andere Schreibweisen verhalten sich gleich.
  • Ein unbekannter Code lässt die Summe unverändert.
  • Eine Summe von 0 bleibt 0. Eine negative Summe wird mit ValueError abgewiesen.

Aufgabe 7A · Plane Tests vor der Implementierung

Notiere für jedes Abnahmekriterium eine Eingabe und das erwartete Ergebnis. Zum Beispiel ergibt apply_discount(100, "SAVE10") den Wert 90.

Beim Test-Driven Development (TDD) schreiben wir Tests vor der Implementierung. Ein fehlgeschlagener Test zeigt zunächst, welches Verhalten noch fehlt. Danach implementieren wir die Funktion und führen die Tests erneut aus.

Lege zunächst src/shopcore/discounts.py mit der folgenden Funktionssignatur an, damit der Import funktioniert. Schreibe dann die Tests in tests/test_discounts.py und führe sie aus. 

def apply_discount(total, code):
      raise NotImplementedError

Importiere pytest sowie apply_discount aus shopcore.discounts. Für Ergebnisse mit Dezimalstellen kannst du pytest.approx verwenden, da float-Berechnungen kleine Ungenauigkeiten enthalten können, zum Beispiel assert apply_discount(35, "SAVE10") == pytest.approx(31.50).

Aufgabe 7B · Implementiere die Funktion

Ersetze den Platzhalter durch deine Implementierung und führe alle Tests erneut aus.

Aufgabe 7C · Überprüfe das Ergebnis

  • Welcher Test hat während der Entwicklung den wichtigsten Fehler aufgedeckt?
  • Testest du jede Codezeile oder die Anforderungen?
  • Erklärt die Testsuite die Funktion für andere Entwicklerinnen und Entwickler?
Kontrollpunkt 7
Das Rabattverhalten ist durch Tests abgedeckt, alle Tests bestehen und deine Implementierung erfüllt die Abnahmekriterien.

Fixtures und ein einfacher Integrationstest

Ziel: Teile sinnvolle Testvorbereitung und prüfe das Zusammenspiel der Funktionen.

Konzept: Fixture

Eine pytest-Fixture stellt einem Test Daten oder eine Testvorbereitung bereit. Ein Test fordert eine Fixture über einen gleichnamigen Funktionsparameter an; pytest stellt sie bereit. Standardmäßig wird sie für jeden Test neu erstellt. Fixtures sind hilfreich, wenn mehrere Tests dieselbe sinnvolle Vorbereitung benötigen.

Aufgabe 9A · Erstelle eine Warenkorb-Fixture

Lege tests/test_checkout.py an und ergänze dort:

import pytest
from shopcore.models import CartItem


@pytest.fixture

Regressionen erkennen und verhindern

Ziel: Verstehe, wie bestehende Tests zuvor funktionierendes Verhalten absichern.

Was ist eine Regression?

Eine Regression entsteht, wenn eine Änderung ein Verhalten beschädigt, das vorher bereits funktioniert hat. Die Änderung kann eigentlich eine andere Aufgabe betreffen, zum Beispiel eine neue Versandregel oder eine Vereinfachung des Codes. Auch nach einer erfolgreichen Änderung müssen die bisherigen Regeln noch gelten.

Beispiel aus ShopCore
Der Versand ist ab 50 € kostenlos. Eine Entwicklerin ändert die Versandberechnung. Danach ist der Versand erst über 50 € kostenlos. Für 60 € funktioniert die Berechnung weiterhin, aber bei genau 50 € werden plötzlich 4,90 € berechnet. Das ist eine Regression: Eine vorher erfüllte Geschäftsregel wurde verletzt.

Was prüft ein Regressionstest?

Ein Regressionstest hält eine Erwartung fest und wird auch nach späteren Änderungen erneut ausgeführt. Ein solcher Test kann vorbeugend für ein wichtiges Verhalten geschrieben werden oder nach einem gefundenen Fehler dafür sorgen, dass dieser nicht unbemerkt zurückkehrt. Deine bisherigen Tests können also bereits als Regressionstests dienen; dafür ist keine besondere pytest-Funktion nötig.

Eine Testsuite ist die Gesamtheit der Tests, die du ausführst. Bestehen alle Tests, weißt du, dass die geprüften Erwartungen erfüllt sind. Das beweist aber nicht, dass alle denkbaren Fehler ausgeschlossen sind.

Aufgabe 11A · Sichere die Versandgrenze ab

Führe zunächst die gesamte Testsuite mit uv run pytest aus. Alle Tests sollten bestehen, bevor du weitermachst. Prüfe, ob deine Tests aus Kapitel 8 bei einem Warenwert von genau 50 € kostenlose Lieferung erwarten. Falls nicht, ergänze in tests/test_shipping.py beispielsweise:

from shopcore.shipping import calculate_shipping_costs


def test_shipping_is_free_at_50():
    assert calculate_shipping_costs(50) == 0

Falls der Import bereits vorhanden ist, füge ihn nicht erneut hinzu. Führe die Tests nochmals aus und überprüfe, dass sie bestehen. Der Grenzfall kann auch bereits Teil eines parametrisierten Tests sein.

Aufgabe 11B · Beobachte eine Regression

  1. Merke dir den ursprünglichen Code. Füge in calculate_shipping_costs(total_price) direkt nach der Funktionszeile vorübergehend die folgenden zwei Zeilen ein:
    if total_price == 50:
        return 4.90
  1. Führe uv run pytest aus. Suche den fehlgeschlagenen Test und vergleiche den erwarteten Wert 0 mit dem tatsächlichen Wert 4,90. Auch weitere Tests können fehlschlagen.
  2. Entferne die beiden eingefügten Zeilen wieder und führe die gesamte Testsuite erneut aus. Alle Tests sollten wieder bestehen.
Wichtig: Ändere nicht die erwartete Versandregel, nur damit der Test besteht. Der Fehler wurde absichtlich im Anwendungscode eingefügt und muss dort wieder entfernt werden. Committe den absichtlich fehlerhaften Zustand nicht.

Kontinuierliche Integration (CI)

Ziel: Verstehe, wie Teams Änderungen regelmäßig zusammenführen und automatisch prüfen.

Warum brauchen Teams CI?

Du kannst uv run pytest auf deinem eigenen Rechner ausführen. In einem Team arbeiten jedoch mehrere Personen an Änderungen. Eine Person könnte vergessen, die Tests auszuführen, oder auf ihrem Rechner andere Voraussetzungen haben. Kontinuierliche Integration (Continuous Integration, kurz CI) bedeutet, dass Änderungen regelmäßig in die gemeinsame Codebasis integriert und dabei automatisch geprüft werden.

Die automatische Prüfung läuft typischerweise in einer separaten Umgebung. Sie ersetzt weder lokale Tests noch die gemeinsame Prüfung des Codes. Sie gibt dem Team zusätzlich eine wiederholbare Rückmeldung zum eingereichten Stand.

Ein möglicher Ablauf

  1. Eine Entwicklerin ändert ShopCore und führt die Tests lokal aus.
  2. Sie erstellt einen Git-Commit und überträgt ihn mit git push an das gemeinsame Repository. Ein Pull Request ist eine Anfrage, Änderungen in einen anderen Branch zu übernehmen.
  3. Ein CI-Dienst startet für den Push oder Pull Request einen zuvor definierten Workflow. Ein Workflow beschreibt, wann die Prüfung läuft und welche Schritte ausgeführt werden.
  4. Der Workflow stellt eine Umgebung bereit, installiert das Projekt und startet die Tests. Anschließend zeigt der Dienst das Ergebnis beim entsprechenden Commit oder Pull Request an.
  5. Das Team prüft das Ergebnis und den Code. Bei Problemen untersucht es die Ausgabe, behebt die Ursache und überträgt eine neue Änderung; der Workflow läuft dann erneut.
Beispiel aus ShopCore
Eine Änderung verletzt die Versandregel bei 50 €. Der Versandtest schlägt in der CI fehl. Das Team sieht die fehlgeschlagene Prüfung, bevor es die Änderung übernimmt, und kann den Fehler korrigieren.

Ergebnisse verstehen

  • Erfolgreich: Alle ausgeführten Schritte waren erfolgreich. Das ist kein Beweis, dass die Anwendung fehlerfrei ist; nur die eingerichteten Prüfungen wurden bestanden.
  • Fehlgeschlagen: Mindestens ein Schritt ist fehlgeschlagen. Öffne dessen Ausgabe: Ein Test kann fehlschlagen, aber auch die Installation oder eine andere Einrichtung kann das Problem sein.
  • Läuft noch: Das Ergebnis liegt noch nicht vor. Warte, bis der Workflow beendet ist.

Optionale Vertiefung · GitHub Actions

GitHub Actions ist ein CI-Dienst von GitHub. Für diese Vertiefung benötigst du ein GitHub-Konto, ein eigenes Repository mit deinem ShopCore-Projekt und aktivierte GitHub Actions. Lege darin die Datei .github/workflows/tests.yml an: 

name: Python-Tests

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - name: Python einrichten
        run: uv python install 3.13
      - name: Projekt installieren
        run: uv sync --dev
      - name: Tests ausführen
        run: uv run pytest

Unter on stehen die Auslöser: ein Push oder ein Pull Request. Der Job test läuft auf einem Linux-Rechner von GitHub. Er lädt den Repository-Inhalt, richtet uv und Python ein, installiert die Abhängigkeiten und führt schließlich dieselbe Testsuite wie lokal aus.

Prüfe mit git remote -v, wohin dein Projekt übertragen wird. Wenn du das ursprüngliche ShopCore-Repository geklont hast, zeigt origin zunächst dorthin. Erstelle auf GitHub ein leeres eigenes Repository und füge es beispielsweise als weiteren Remote hinzu. Ersetze die Platzhalter durch deinen GitHub-Namen und den Namen deines Repositorys:

git remote add mein-shopcore https://github.com/DEIN-NAME/DEIN-REPOSITORY.git

Falls du bereits einen geeigneten Remote eingerichtet hast, verwende stattdessen dessen Namen. Prüfe mit git status, ob deine Anwendung, Tests, Abhängigkeiten und die Workflow-Datei committed sind; übertrage dann den aktuellen Branch. GitHub kann eine Anmeldung verlangen: 

git push -u mein-shopcore HEAD

Wenn dein Remote anders heißt, ersetze mein-shopcore im Befehl entsprechend.

Öffne dort den Reiter Actions, wähle den Lauf Python-Tests und öffne den Job test. Sieh dir die Ausgabe des Schritts Tests ausführen und den Status an. Bei einem Fehler lies auch die Ausgabe früherer Schritte. Nach einer Korrektur startet ein neuer Push einen neuen Lauf.

Dies ist ein Lehrbeispiel. Prüft vor der Übernahme in ein gepflegtes Repository die aktuellen Action-Versionen und die uv-Empfehlungen für Workflows.

Begriffe rund ums Testen

  • Testfall: eine bestimmte Situation und das dafür erwartete Verhalten.
  • Assertion (Prüfung): Kontrolle, ob eine Bedingung wahr ist.
  • Grenzfall: eine ungewöhnliche oder grenzwertige Eingabe, die geprüft werden sollte.
  • Regression: eine Änderung, durch die zuvor funktionierendes Verhalten beeinträchtigt wird.
  • Refactoring: strukturelle Änderung ohne beabsichtigte Änderung des Verhaltens.
  • Fixture: wiederverwendbare Testvorbereitung oder Daten, die Tests bereitgestellt werden.
  • CI: automatisierte Prüfungen während der Integration von Codeänderungen.
